# A collector's Discogs collection and wantlist are synced on demand, hide what they list and fade the other versions

fader-ui#116. A collector already has, or wants, the releases on their Discogs lists, so Explore should not offer them, and the other versions of those releases are not interesting either.

- **On demand, one job.** `POST /me/discogs-profile/refresh` (the Refresh button on Home) queues one `discogs_sync` job at priority 5 (`SYNC_PRIORITY`) on the collector's own lane, behind inline requests and ahead of enrichment (0). It pages the wantlist and then the collection, 100 to a page, 1.1 s apart, and answers `202` at once. The profile status (`GET /me/discogs-profile`) carries `sync.status` (`idle`, `running`, `failed` with a message), derived from the latest job of the run `discogs-sync:<uid>`; a sync already queued or running is not started twice. It replaces the counts-only `discogs_profile` job as the Refresh action. That job stays behind `POST /me/discogs-profile/counts`, which the home card uses once to fetch the counts it shows (and the first-sync confirmation quotes) before anything has been synced.
- **Nothing is written until every page is in.** A 429 or a 5xx follows the queue's pause rules (`0002`), which run the job again from the first page; a failed sync leaves the previous mirror as it was.
- **One transaction.** The lists are mirrored into `collection_items` and `wantlist_items` (primary key `(uid, release_id)`, one row per release; ids not in the catalogue are kept, and `master_id` is null when Discogs sends `0`). For each release now on either list: add `hidden_releases(uid, release_id)`; delete the collector's release-kind fade on it; if it has a master and the collector has no fade on that master, insert one (`pending`, or `done` when the master's versions are already stored) and queue the existing fade lookup at priority 5, which fades every other version. A release without a master is only hidden. A release that left both lists loses its hidden row; the master fade stays, so the whole master, that release included, is faded. A master fade the collector made themselves is never touched. The profile counts are rewritten from the mirrored lists and `discogs_profiles.last_synced_at` is set.
- **Private.** Every table is keyed by `uid`, and nothing about a collector's lists goes on the shared `releases` table (no `source` column there). The profile row, and so `last_synced_at`, goes when the token is replaced or removed, so the next sync asks for confirmation again.
- **First sync.** While `last_synced_at` is null the UI asks for confirmation (it can fade several hundred masters, undone one at a time on the Faded page).
- **Not part of this.** The read side of Hidden (fader-ui#118) and the wantlist page (fader-ui#144). The Bandcamp, file and scrape imports will write `hidden_releases` through the same path. Because the table has no source column, a sync also removes a hidden row another source wrote for a release that left both Discogs lists; revisit when the second writer exists.
- **Checked live (2026-10-17):** `master_id` is `0` for a release without a master, and the list payloads have no `tracklist` and no `num_for_sale` (see `docs/reference/discogs-api.md` in `fader-ui`).

- **Availability (fader-ui#143).** After a sync commits, `queueWantlistEnrichment` queues a `release_detail` job at priority 1 (above background enrichment at 0, below the sync and searches at 5) for each wantlist release that is not stored, was never enriched, has no `num_for_sale_at` or has one older than a day (the threshold is on the shared `releases` column, so another collector's fetch counts). The jobs use the run label `wantlist-availability:<uid>` and no `enrichment_runs` row, so a saved-filter run neither cancels nor finishes them; a release already queued by any job, or marked `missing_at`, is skipped. The handler stores `num_for_sale` and `num_for_sale_at` (and inserts the full row when the release was not stored). Only the Discogs wantlist is enriched; the page that shows the count is fader-ui#144.

- **Removing from the wantlist (fader-ui#144).** The wantlist page fades a release by first taking it off the Discogs wantlist: `DELETE /wantlist/{releaseId}` queues a `wantlist_remove` job at inline priority (10, ahead of the sync and enrichment) that calls `DELETE /users/{username}/wants/{release_id}` (confirmed live 2026-10-17), then drops the mirror row, the hidden row (unless the release is also in the collection) and rewrites the profile count. Otherwise the next sync would delete the release fade and fade its master again. The UI then calls `POST /fade`.
