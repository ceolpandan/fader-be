# Digital stores are Strategies behind one check, and a check is a request the collector waits on

fader-ui#160. A collector wants to know which wantlist items can be bought digitally, starting with Bandcamp; Traxsource and Beatport may follow.

- **Strategy, not Bridge.** A `DigitalStore` (`src/digital/types.ts`) has one adapter per store (`src/digital/bandcamp/`). Bridge fits two hierarchies that vary on their own; here only the store varies. A store declares the searches it can do (`searchReleases`, `searchTracks`), so a track-first store leaves out the album search. Adding a store is an adapter plus one line in `createDigitalStores`.
- **The policy is shared.** `checkRelease` owns what a check does: search the album first (`item_type=a`), and only when that misses search every track (`item_type=t`), then decide whether a hit counts. An adapter only fetches and parses a page; it knows nothing about Discogs.
- **A hit counts** when its title matches (`normalise`, plus a trailing `(Original Mix)` optional on either side) and its artist is one of the release's, with `feat.`, `&`, `and` and `,` read as the same join. A compilation (`Various`) names no artist to check: its album is not searched, and a track counts when it is on an album of the same title. The top 3 rejected candidates of every miss are logged, so the rules can be loosened after a test run.
- **Bandcamp needs a browser's headers.** Searching needs no login, but a request without a browser's headers and cookies gets a "Client Challenge" page back with a 200. The collector pastes a curl (`PUT /digital/{store}/session`); it is parsed into headers and cookies, the login cookies (`identity`, `js_logged_in`) are dropped, and the rest is kept **in memory for 24 hours**, per collector and store: its short-lived cookies (Stripe's session id) are stale by the next day, and a stored secret is not worth keeping for a value that is worthless tomorrow. A restart means pasting again. A challenge page or a 403 means the session is stale (`StoreSessionExpiredError`), and the API answers 409 `store_session_required`.
- **One lane per store.** Every request to a store goes through a `PacedLane`: one at a time, at least 1.2 s apart, for the whole server (the store sees our address, not the collector).
- **A check is synchronous for now.** `POST /digital/{store}/matches` answers when the check is done, about a second per request (a 12-track release that is not found takes about 16 s). That is a person waiting on one item, like an **Inline request**. It does not use the Discogs queue, which is for Discogs. A scan of the whole wantlist (fader-ui#161) needs progress, pause and resume, and will run as a run of its own on the same lane; a 429, 5xx or network error is a 503 here and is retried by that scan, not by this call.
- **Results are shared.** `digital_matches(release_id, store, status, url, tracks, checked_at)` is keyed by release and store, like the release itself, so one collector's check benefits every collector who wants it. `status` is `album`, `tracks` or `none`; `none` is stored so a rescan can skip it. `tracks` holds only the tracks that were found (Discogs position, title, URL) and `track_count` how many were searched, so the card can say "3/5". A recheck overwrites the row. Only wantlist items with a `releases` row can be checked: an **Unmatched** item has no tracklist and nowhere to store the result.
- **Not part of this.** Scanning the whole wantlist (fader-ui#161) and filtering the wantlist by availability (fader-ui#162).
